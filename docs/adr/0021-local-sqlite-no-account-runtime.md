# ADR-0021: Use a local SQLite, no-account runtime

- **Status:** Accepted; supersedes ADR-0004, ADR-0005, ADR-0013, ADR-0014, and the database-backup portions of ADR-0019
- **Date:** 2026-07-03

## Context

The product is a downloadable personal tool. Requiring Docker, a PostgreSQL server, database volumes, credentials, and account bootstrap makes that goal unnecessarily complex. The relational model is still valuable because provenance, immutable versions, deletion, and cross-record ownership require transactions and constraints.

## Decision

Ship one local-only, single-user modular monolith. Bundle Node.js with the Windows ZIP, bind the application to `127.0.0.1`, derive one trusted local principal, and provide no sign-in or remote/shared mode. Use Node's built-in `node:sqlite` API and reviewed SQLite migrations. Store structured data in `vitae.sqlite`; store uploaded/generated bytes in a sibling `files/` folder. Run MVP jobs in-process with bounded child processes where parser isolation is required.

The launcher creates the data folder and credential-encryption key automatically. Stopping or replacing application binaries never deletes data. A coordinated manual backup is a copy of the complete data folder while stopped; in-product portability remains the stable logical export format.

## Alternatives considered

Raw JSON or Markdown files are transparent but do not safely provide multi-record transactions, foreign keys, unique constraints, concurrent-write handling, or indexed evidence/provenance queries. PostgreSQL provides these properties but requires a server and operational setup. Docker hides some installation details but remains a large runtime prerequisite. A desktop-shell rewrite would add packaging and security surface without improving the current browser-based local workflow.

## Consequences

Users download, extract, and start the tool without an account or external service. SQLite is itself an ordinary portable file, but it must be copied together with the files folder for a complete physical backup. The release is intentionally not a remotely exposed web service and does not support multiple simultaneous users or high-availability deployment. Database queries and migrations are SQLite-specific.

## Security and privacy implications

Loopback binding is a hard startup invariant because there is no authentication boundary. File permissions are restricted where the operating system supports it. Provider secrets are encrypted with a generated local key. Inputs and model output remain untrusted. Logs exclude document content, prompts, outputs, credentials, and tokens. Backups contain sensitive personal data and are the user's responsibility to protect.

## Revisit conditions

Revisit only if measured demand requires remote/shared use, multi-process write throughput exceeds SQLite's supported local pattern, or Node removes/stabilizes the selected API in an incompatible way. A remote edition would require a separate threat model and authentication decision; it must not silently weaken this local release.
